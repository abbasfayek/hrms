--------------------------------------------------------------------------------
Branch Isolation closes the outstanding Branch-Isolation issue on top of closed
Phases 1-8 baselines. No new Business Policies, no Formula changes, no State

(scripts/final-branch-isolation-gate.mjs — 75 assertions, S1..S10).

3. ENFORCEMENT MODEL (engine-level, UI-agnostic)
--------------------------------------------------------------------------------
  Guard order (unchanged first two, new third):
    1. permission  — user holds the permission for the action
    2. scope       — every batch item within the user's assigned company/branch
    3. CONTEXT     — the batch's real identity must match the CURRENT branch:
                     - identity-less batch            → branch_context_required
                     - assigned-scope mismatch        → company/branch_mismatch
                     - UI-context mismatch            → company/branch_mismatch
                      (super_admin = global authority, exempt by design)

  Batch identity resolution: batch.companyId/branchId first, else the first
  item's companyId/branchId (legacy + generated batches always carry per-item
  identity). p5/p6 permission-first expectations are preserved (denials carry
  layer: 'permission' before any context logic runs).

  The Current Branch context is the SAME { companyId, branchId } the UI sends
  as `context` on every guarded transition — the test drives the exact shape a
  user action produces, so a denial under test equals a denial in production.

4. FINAL GATE — 10 ACCEPTANCE POINTS (all verified)
--------------------------------------------------------------------------------
  S1  Engine-level branch context enforcement: sensitive ops on identity-less
      batches refused (branch_context_required); wrong-context correction
      refused before any state check; correct-context ops pass.
  S2  Real E2E Baghdad workflow: generate → submit → approve → disburse →
      archive → stored Paid + Archived.
  S3  Cross-branch protection (working in Baghdad cannot touch Erbil):
      failed submits never store; failed approve/disburse/archive leave the
      stored Baghdad record byte-identical.
  S4  Real E2E Erbil workflow WITH a Returned/re-submit leg and reverse
      protection (working in Erbil cannot touch Baghdad); Baghdad remains
      Paid + Archived throughout.
  S5  Same employee (same full name) in both branches → two independent payroll
      records per real branch, never mixed.
  S6  Archive integrity: archived batches retain companyId, branchId,
      employeeId(s) and payrollPeriodId permanently; branchId is never re-read
      from the currentSelectedBranchId at display time.
  S7  Switching branches never rewrites/deletes/replaces stored payrolls
      (raw storage byte-identical across switches; both batches stay
      Paid + Archived on round-trip).
  S8  Reports / Excel / print take rows exclusively from the stored batch whose
      companyId+branchId equal the current context → no cross-branch leakage;
      row sum == batch net.
  S9  Audit trail: every payroll event (success AND denied) carries companyId,
      branchId, payrollId, employeeIds, action, actor, timestamp; paid events
      carry the REAL branch, not the UI's currentBranchId; hash chain valid.
  S10 Full regression green.

  Scenario as ordered: Baghdad → generate → submit → approve → disburse →
  archive → switch to Erbil → generate → submit → reject(Returned) → resubmit →
  approve → disburse → archive → switch back to Baghdad → BOTH remain
  Paid + Archived, each with its own workforce, amounts and audit trail.
