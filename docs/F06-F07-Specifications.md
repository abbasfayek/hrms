# مواصفات المتطلبات الفنية: F-06 و F-07 (Technical Specifications)

> [!IMPORTANT]
> هذه الوثيقة تمثل **مواصفات فنية وتصميمية فقط (Specification)** وفقًا لقرارات Post-P10 Readiness Audit.
> **لم يتم تطبيق أي كود برمجي لهذين البندين**، ويبقى العمل متوقفًا بانتظار الاعتماد الرسمي.

## 1. Finding F-06: دورة تدقيق ومقارنة التعديلات عند إعادة الإرسال (Reject → Correct → Resubmit Workflow)

### 1.1 السلوك الحالي (Current Behavior)
* عند رفض مسير رواتب من قبل المدقق/المدير (`rejected`)، يتم تغيير حالته وتخزين سبب الرفض (`rejectionReason`).
* يستطيع المحاسب/مسؤول الرواتب فتح المسير المرفوض وتعديل البنود أو إعادة حسابه بالكامل (`Recalculate`).
* خلال إعادة الحساب أو التعديل، تُسحب بيانات حية جديدة (مثل سجلات حضور محدثة أو أقساط قروض)، مما قد يُغيّر قيم صافي الرواتب أو الاستقطاعات.
* **الفجوة الحالية:** لا توجد آلية تتبع فروقات (Diff / Versioning) تحفظ نسخة مجمدة من المسير وقت الرفض (`rejectionSnapshot`) لمقارنتها بالنسخة الجديدة المعدلة (`resubmission`). المدقق عند وصول المسير إليه مجددًا لا يرى ملخصًا بما تم تصحيحه ولا الفروقات المالية المحددة، مما يزيد مخاطر تسلل تعديلات غير معتمدة أو عدم معالجة سبب الرفض بدقة.

### 1.2 السلوك المقترح (Proposed Behavior)
1. **تجميد نسخة الرفض (Rejection Snapshot):** فور انتقال المسير إلى حالة `rejected`، يتم أخذ لقطة غير قابلة للتعديل تحتوي على:
   * بيانات بنود المسير كاملة وقت الرفض.
   * إجمالي المسير (Gross / Net / Deductions / Allowances).
   * هوية الرافض، تاريخ الرفض، وسبب الرفض.
2. **عداد الإصدارات (Revision Counter):** عند إعادة فتح المسير وتعديله ثم إعادة إرساله للاعتماد (`pending_approval`)، يرتفع رقم الإصدار تلقائيًا (`revision: revision + 1`).
3. **سجل الفروقات والتصحيحات (Audit Delta Summary):** عند إعادة الإرسال (`Resubmit`)، يتم توليد سجل مقارنة تلقائي (Delta) يوضح:
   * الموظفون الذين طرأ تغيير على رواتبهم (صافي الراتب القديم مقابل الجديد والفرق).
   * البنود المضافة أو المحذوفة أو المعدلة.
   * الفارق الإجمالي في تكلفة المسير بين النسخة المرفوضة والنسخة المعاد إرسالها.
4. **عرض الفروقات للمدقق (Reviewer Diff View):** في واجهة مراجعة المسير (`PayrollView`)، تظهر للمعتمد شارة "مسير معاد إرساله (إصدار X)" مع إمكانية فتح نافذة مقارنة فورية تبرز سبب الرفض والتعديلات التي تمت لمعالجته.

### 1.3 أثر نموذج البيانات (Data Model Impact)
* **في كائن مسير الرواتب (`payroll batch`):**
  ```javascript

    "revision": 2, // يبدأ من 1، ويزداد عند كل إعادة إرسال بعد الرفض
    "rejectionHistory": [
      {

        "rejectedAt": "2026-09-12T18:00:00.000Z",
        "rejectedBy": "user_mgr_01",
  ```

### 1.4 أثر دورة العمل (Workflow Impact)
* **دورة الحالات:**
  `Draft` → `Pending Approval` → `Rejected` (حفظ Rejection Snapshot) → `Draft / Under Correction` → `Resubmit` (حساب Delta وزيادة Revision) → `Pending Approval` → `Approved`.
* منع إعادة الإرسال دون إدخال ملاحظات تصحيحية (`correctionNotes`) عند وجود رفض سابق.
* منع تعديل أو حذف `rejectionHistory` أو `snapshot` من قبل أي مستخدم (تُعامل كبيانات نظام ثابتة).

### 1.5 متطلبات التدقيق الأمني والرقابي (Audit Requirements)
* تسجيل حدث تدقيق إلزامي `PAYROLL_REJECTED` يشمل: `batchId`, `revision`, `reason`, `rejectedBy`, `hashSnapshot`.
* تسجيل حدث تدقيق إلزامي `PAYROLL_RESUBMITTED` يشمل: `batchId`, `oldRevision`, `newRevision`, `affectedEmployeesCount`, `netDelta`, `resubmittedBy`.
* منع تداخل التعديل: إذا كان المسير قيد التعديل بواسطة محاسب آخر أو قيد المراجعة، يتم تفعيل فحص التزامن المتفائل (`expectedRevision`) لمنع الكتابة المتزامنة المتعارضة.

### 1.6 سيناريوهات اختبار التراجع (Regression Scenarios)
1. **سيناريو دورة الرفض وإعادة الإرسال الكاملة:** التحقق من إنشاء `rejectionHistory` وحفظ الـ snapshot سليمًا دون فقدان أي بند.
2. **سيناريو حساب الفروقات (Delta Accuracy):** التحقق من دقة حساب فرق صافي الراتب عند تعديل موظف واحد، أو عدة موظفين، أو إضافة موظف جديد.
3. **سيناريو مناعة التاريخ القديم ضد التعديل:** التأكد من عدم تأثر `snapshot` المرفوض بأي عمليات تعديل لاحقة على المسير.
4. **سيناريو منع التعارض والتزامن (Concurrent Resubmit):** محاولة إرسال تصحيحين في نفس اللحظة بنفس رقم الـ revision، والتأكد من رفض أحدهما وحماية سلامة البيانات.

## 2. Finding F-07: تجميد أسعار الصرف على مستوى البنود والتقارير التاريخية (Historical Exchange Rate Snapshotting)

### 2.1 السلوك الحالي (Current Behavior)
* عند احتساب مسير الرواتب، يتم تثبيت أسعار الصرف أو عملة الدفعة على مستوى مسير الرواتب ككل (`batch.ratesSnapshot` أو `batch.currency`).
* ومع ذلك، فإن بعض شاشات التقارير المجمعة (`ReportsView`) أو واجهات طباعة القسائم (`Payslips`) تعتمد في بعض السيناريوهات على الاستعلام المباشر من إعدادات الشركة الحالية (`settings.exchangeRates`) أو تفترض سعر الصرف = `1.0` عند عدم وجود حقل صريح على مستوى السجل الفردي (`item`).
* **الفجوة الحالية:** في حال قامت الشركة بتحديث جدول أسعار صرف العملات لاحقًا (مثل تغير سعر صرف الدولار أو اليورو مقابل الريال)، فإن إعادة فتح تقرير تاريخي لمسير تم صرفه قبل 6 أشهر قد يستخدم سعر الصرف الجديد بدلاً من سعر الصرف الفعلي وقت اعتماد وصرف المسير، مما يؤدي إلى تشويه التقارير المالية ومطابقات الأرصدة.

### 2.2 السلوك المقترح (Proposed Behavior)
1. **تجميد سعر الصرف في كل بند (Item-Level Rate Snapshotting):**
   * كل سجل راتب موظف (`payrollItem`) يجب أن يتضمن بصورة إلزامية حقولاً واضحة وغير قابلة للتغيير:
     * عملة الراتب الأصلية للموظف (`originalCurrency`).
     * سعر الصرف المعتمد مقابل عملة الأساس وقت احتساب المسير (`exchangeRateToBase`).
     * القيمة المعادلة بعملة الأساس (`baseCurrencyGross`, `baseCurrencyNet`).
     * تاريخ/مرجع لقطة أسعار الصرف (`ratesSnapshotDate` / `snapshotVersion`).
2. **عزل التقارير المالية عن الإعدادات الحية للعملات:**
   * يجب منع شاشات التقارير والطباعة التاريخية منعًا باتًا من قراءة `settings.exchangeRates` الحالية عند معالجة أي مسير معتمد أو مدفوع (`approved` أو `paid`).
   * التقارير التاريخية تعتمد حصرًا على أسعار الصرف المخزنة داخل المسير والبنود (`item.exchangeRateToBase` أو `batch.ratesSnapshot`).
3. **حماية التعديل بأثر رجعي:**
   * فرض حظر في الخادم (`server-authz.mjs` / `settings engine`) يمنع تعديل أسعار الصرف التاريخية أو إعادة تقييم مسيرات الرواتب المغلقة.

### 2.3 أثر نموذج البيانات (Data Model Impact)
* **في كل بند داخل `payroll.items[]`:**
  ```javascript
  {
    "employeeId": "EMP012",
    "salaryCurrency": "USD",
    "baseCurrency": "SAR",
    "exchangeRate": 3.75, // سعر الصرف المجمد وقت الاحتساب
    "baseCurrencyEquivalent": {
      "basicSalary": 18750, // 5000 USD * 3.75
      "gross": 22500,
      "totalDeductions": 1875,
      "net": 20625
    },
    "rateSnapshotRef": {
      "snapshotDate": "2026-08-31T23:59:59.000Z",
      "source": "company_settings"
    }
  }
  ```
* **في كائن مسير الرواتب (`payroll batch`):**
  * التأكد من وجود `ratesSnapshot: { [currencyCode]: rate }` كامل ومغلق ولا يتم مسحه أو تجاوزه.

### 2.4 أثر دورة العمل (Workflow Impact)
* محرك الرواتب (`wageEngine` / `payrollEngine`) أثناء مرحلة التوليد يضمن تضمين لقطة سعر الصرف لكل بند.
* واجهة التقارير (`ReportsView`) وواجهة القسائم (`BatchPayslipsPrintModal`) تتحقق من وجود `item.exchangeRate`؛ إذا كان المسير قديمًا جدًا ولا يحتوي على الحقل على مستوى البند، يتم الرجوع إلى `batch.ratesSnapshot` كـ Fallback حصري، ولا يُسمح نهائيًا بالرجوع إلى `settings.exchangeRates` الحية الحالية.

### 2.5 متطلبات التدقيق الأمني والرقابي (Audit Requirements)
* تسجيل مصفوفة أسعار الصرف بالكامل في حدث تدقيق اعتماد المسير `PAYROLL_APPROVED` و `PAYROLL_PAID`.
* إطلاق تحذير تدقيقي (Audit Warning / Discrepancy Log) إذا حاول أي استعلام تقريري إعادة احتساب مبالغ مسير مدفوع بأسعار صرف لا تطابق اللقطة المحفوظة.

### 2.6 سيناريوهات اختبار التراجع (Regression Scenarios)
1. **سيناريو ثبات التقارير بعد تغيير سعر الصرف:**
   * إنشاء وصرف مسير رواتب بعملة أجنبية بسعر صرف (1 USD = 3.75 SAR).
   * تعديل سعر الصرف في إعدادات الشركة لاحقًا إلى (1 USD = 4.00 SAR).
   * استخراج تقرير الرواتب وقسائم الرواتب للمسير القديم: التأكد بنسبة 100% أن المبالغ وقيم المعادل بعملة الأساس بقيت محسوبة على 3.75 SAR دون أي تغيير.
2. **سيناريو اتساق البنود الفردية مع إجمالي الدفعة:**
   * التحقق من تطابق مجموع `baseCurrencyNet` لجميع بنود الموظفين الفردية مع `totalNetBase` على مستوى الدفعة.
3. **سيناريو الـ Fallback الآمن للبيانات القديمة (Legacy batches):**
   * اختبار مسير قديم لا يحتوي على سعر الصرف في البند: التأكد من سحب السعر من `batch.ratesSnapshot` فقط ورفض استخدام سعر اليوم.
