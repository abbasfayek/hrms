--------------------------------------------------------------------------------
Phase 6 delivers the FULL official Payroll Workflow end-to-end, on top of the
closed Phase 1-5 baselines:

  Draft --submit--> Under Audit --approve--> Approved (Payment Queue point)
                           |                        |
                        reject                   disburse  (approved -> paid)
                           |                        |
                           v                        v
            Returned / Needs Correction           Paid --archive--> Archived

  Returned --correction--> (corrected, amounts preserved)
          --resubmit--> Under Audit (NEW audit attempt, SAME record, no new payroll)

Payroll workflow ONLY. No EOSB / Clearance / Dashboard / Reports changes,
no Phase 7/8 work, no new business policies, no formula changes.

3. WORKFLOW (verified end-to-end through the REAL public surfaces: guard stack
   + Phase 1 state machine + storage + Phase 5 audit trail + Phase 4 currency
   snapshots + Phase 3 data model)
--------------------------------------------------------------------------------
  Stage                 Engine                            Audit event
  -------------------   -------------------------------   --------------------
  create (draft)        generateMonthlyPayroll / manual    created
  submit                transitionPayrollGuarded(draft->under_audit)   submitted
  audit notes save      plain re-save (no status change)  (none - no fabrication)
  reject/return         transitionPayrollGuarded(under_audit->rejected) rejected
  correction (recalc)   recordPayrollCorrectionGuarded    corrected
  resubmit              transitionPayrollGuarded(rejected->under_audit) resubmitted
  approve               transitionPayrollGuarded(under_audit->approved) approved
  pay / disburse        transitionPayrollGuarded(approved->paid)         paid
  archive               archivePayrollBatchGuarded(paid)                 archive
  any forbidden step    reportDenied -> storage hook       denied (outcome 'denied')

Transition table (Phase 1, unchanged): draft->under_audit;
under_audit->approved|rejected; rejected->under_audit; approved->paid; paid->[] (terminal).

4. GUARDS (permission → scope → state, always all three)
--------------------------------------------------------------------------------
  Payroll Admin (payroll.generate/edit/submit/export):
    May create/edit/correct/submit/export. May NEVER approve, reject, pay,
    archive (permission error at layer 'permission').
  Audit Reviewer (payroll.approve/reject/cancelPayment):
    May approve or reject/return. May NEVER create/edit/submit/pay/archive.
  Payments Officer (payroll.disburse):
    May only disburse an APPROVED payroll (duplicate pay, draft/under_audit/
    rejected pay all blocked at layer 'state').
  Super Admin: everything; still bound by the state machine (no modify after
    approval, no archive before paid, no re-archive).
  Out-of-scope users: scope_violation at layer 'scope' (e.g. company_hr with
    assignedCompanyId comp-2 cannot touch a comp-1 batch though permission passes).

--------------------------------------------------------------------------------
5. REJECT / RETURN BEHAVIOUR
--------------------------------------------------------------------------------
  * amounts never zeroed: rejectedSnapshot captured at reject, `isAmountsCleared`
    forced false, every monetary value preserved (asserted == pre-reject value)
  * rejectedBy / rejectedAt / rejectionReason / auditNotes attached
  * returnState = 'needs_correction' -> the record is Returned / Needs Correction,
    never a fresh unrejected draft
  * Rejected version linked (V..) + audit attempt marked result 'returned'
  * REJECTED audit event carries reason + rejection reference incl. sealed
    rejected snapshot

--------------------------------------------------------------------------------
6. CORRECTION
--------------------------------------------------------------------------------
  recordPayrollCorrectionGuarded (edit+scope guard, engine:
  recordPayrollCorrection). Old->new change per monetary field is computed
  against the rejected snapshot (employeeId, field, oldValue, newValue), stamped
  with user, timestamp, reason; appended to batch.corrections + a 'corrected'
  version (Rejected -> Corrected -> Resubmitted chain with explicit
  prevVersionId/nextVersionId); auditAttempt result 'corrected'. Audit event
  CORRECTED carries the changes array. History is never overwritten; the sealed
  Phase 3 baselineSnapshot (first submission) stays untouched.

--------------------------------------------------------------------------------
7. RESUBMIT
--------------------------------------------------------------------------------
  same record (id + month preserved; no duplicate payroll ever created),
  status back to under_audit, returnState='resubmitted', resubmittedBy/At,
  a NEW audit attempt (result 'under_audit'), RESUBMITTED audit event (never a
  second SUBMITTED), resubmissionRounds() >= 1.

--------------------------------------------------------------------------------
8. PAYMENT ELIGIBILITY / PAID
--------------------------------------------------------------------------------
  * only approved can be paid: draft / under_audit / rejected / paid all
    generate disburse_requires_approved (or paid->[] terminal) denials
  * paid stamps paidBy/paidAt/releaseStatus='released' + paymentReference
    (status approved->paid queue point only; the full Payment entity stays a
    later phase - no invented payment business logic)
  * duplicate payment impossible (paid->paid denied; exactly one PAID event)
  * PAID event carries paymentReference + actor + frozen financial snapshot

--------------------------------------------------------------------------------
9. ARCHIVE
--------------------------------------------------------------------------------
  * only after Paid (status stays 'paid'; archival flag archived=true + stamps
    + archiveReference; financial read-only)
  * re-archive denied at engine level ('already_archived'); archive-before-paid
    denied at the guard (layer 'state'); ARCHIVE audit event reasonKind 'archive'

--------------------------------------------------------------------------------
10. AUDIT TRAIL INTEGRATION (Phase 5)
--------------------------------------------------------------------------------
  * exactly one honest event per real transition; plain re-saves emit nothing
  * every denial is audit-recordable as `denied` (never a success event)
  * append-only chain verified (verifyAuditTrail) after EVERY step
  * events link versionId (V{revision}) + auditAttempt (attempt/result) +
    financial snapshot (never re-priced)

--------------------------------------------------------------------------------
11. CURRENCY SNAPSHOT PRESERVATION (Phase 4)

  * financial view asserted identical across approve -> paid -> archive
  * corrected/returned records never repriced: rejectedSnapshot + baseline

13. BUGS FOUND & FIXED DURING PHASE 6 (REAL BUGS, REAL UI SURFACES)
--------------------------------------------------------------------------------
  Bug #1 — stale last-known-state baselines after data wipe:
  storage.clearAllData() / resetToDefaults() did not clear the in-memory
  last-known-state payroll baselines (`this._payrollBaselines`). After a data
  clear or factory reset, re-creating the SAME month as a new draft was audited
  as a stale 'updated'/'paid' transition instead of a genuine CREATED record.
Fixed by clearing the map in both wipe paths (additive; verified by P6 E2E
   isolation and all regression gates).

--------------------------------------------------------------------------------
13b. BUG FIXED #2 — CORRECTION ERASED SEALED HISTORY (found by manual-browser
     verification of the returned-card flow; fix commit d6a90b3)
--------------------------------------------------------------------------------
  SYMPTOM: pressing "Recalculate & Record Correction" on a Returned card then
  Resubmitting silently dropped the record's `baselineSnapshot`,
  `rejectedSnapshot` and version chain; `originalFinancialValues()` returned
  NULL and the chain was truncated to [corrected] instead of
  [under_audit, rejected, corrected]. Historical financial snapshots were lost.
  ROOT CAUSE: recordPayrollCorrection(prev, next) copied only the rejection
  metadata from prev (rejectedBy/At, rejectionReason, auditNotes). The real UI
  hands `next` = a FRESH generateMonthlyPayroll() object (id/month/totals/
  items/totalsByCurrency/createdAt only) — no baselineSnapshot, no
  rejectedSnapshot, no versions, revision 0 — so the old code wrote over the
  stored history instead of extending it.
  WHY UNDETECTED EARLIER: the original E2E corrected a CLONE of the rejected
  batch (carried all fields), so every attempt/version/baseline assertion
  passed (118/118). Only the jsdom browser-level driver that fed the REAL
  PayrollView recalc path exposed the regression; a minimal two-pipeline probe
  (PIPELINE A = fresh object, PIPELINE B = clone) reproduced it deterministically.
  FIX (engine data-model layer, NOT a UI-only patch): the existing history is
  authoritative. recordPayrollCorrection now (a) converges on `prev` for
  baselineSnapshot / rejectedSnapshot whenever `next` carries none,
  (b) seeds `next.versions` from prev's chain and only EXTENDS it (dedup by
  versionId), (c) continues revision numbering from prev (never restarts at 1).
  Any history-less new object can now only append to a Returned record — it can
  never erase existing history. No formula / policy / state-machine /
  permission / currency changes.
  REGRESSION TEST: p6-tests.mjs section F reproduces the EXACT real-UI path
  (CREATE -> SUBMIT -> REJECT -> salary edit 6000 -> 6500 -> FRESH
  generateMonthlyPayroll() correction -> RESUBMIT) and FAILS if any of
  baselineSnapshot / rejectedSnapshot / versions / auditAttempts /
  originalFinancialValues disappear, or if the chain, single-record identity,
  old/new change log, reason/user stamps, currency segment or audit sequence
  regress (F0-F23). Old tests untouched; P6 grew 118 -> 142 assertions.

15. DECISIONS / NOTES
--------------------------------------------------------------------------------

    SOLE correction entry point and records old->new diffs; on a guard denial
    the UI now ABORTS instead of silently saving a fresh draft over the
    Returned record (previous dead-code fallback would have bypassed the guard).
  * Payment Queue: only the approved->paid link is implemented (spec: full
    Payment entity is a later phase).
  * Export remains permission-gated in the UI (payroll.export); the state
    machine does not restrict export.

  * Manual-browser verification of the returned-card flow (jsdom driver driving
    the REAL PayrollView) was executed: create -> submit -> reject -> recalc &
    record correction (6000 -> 6500) -> resubmit all passed EXCEPT the sealed-
    history loss documented in §13b; that bug was fixed and is now covered by
